# SQLite to PostgreSQL Conversion

## Decision

PostgreSQL is the recommended production system of record. Curais relies on relational ownership, active memberships, bounded consent grants, transactional profile replacement, uniqueness, and auditable authorization.

## Schema mapping

| SQLite | PostgreSQL |
| --- | --- |
| `TEXT` application ID | `uuid` generated by the application or `uuid` default |
| RFC 3339 timestamp text | `timestamptz NOT NULL` |
| role/status `CHECK` | constrained text initially; native enum only if migrations remain easy |
| `INTEGER` version | `bigint NOT NULL` |
| `?` placeholder | `$1`, `$2`, ... |
| single process connection | bounded pool with timeouts and health metrics |

Keep `users`, `auth_accounts`, `auth_sessions`, `patient_profiles`, `patient_contacts`, `patient_allergies`, `patient_medications`, `clinics`, `clinic_memberships`, `sharing_grants`, `medical_history_entries`, `family_links`, `appointments`, `encounters`, `prescriptions`, `lab_orders`, and `audit_events` normalized. Add partial indexes for active grants and memberships.

```sql
CREATE UNIQUE INDEX sharing_grants_active_unique
ON sharing_grants(patient_id, clinic_id, scope)
WHERE status = 'active';

CREATE INDEX doctor_active_memberships
ON clinic_memberships(user_id, clinic_id)
WHERE status = 'active';
```

## Application work

1. Add `PostgresRepository` adapters for `profile.Repository` and `access.Repository`.
2. Use `pgx/v5` with explicit transaction isolation and statement timeouts.
3. Move DDL to numbered immutable migrations; never run ad-hoc `CREATE TABLE` on production startup.
4. Run identical repository contract tests against SQLite and PostgreSQL.
5. Require optimistic concurrency (`version`) for clinical writes.
6. Use a separate least-privilege migration role and application role.

## Data migration

1. Put the local source in read-only maintenance mode.
2. Export each table to typed newline-delimited JSON or CSV with row counts and SHA-256 manifests.
3. Create PostgreSQL schema and constraints before loading.
4. Load parents before children: users, clinics, profiles, memberships, health lists, grants, audits.
5. Validate counts, foreign-key orphans, uniqueness, active grant semantics, timestamps, and latest profile versions.
6. Run authorization probes: no grant, active grant, revoked grant, disabled membership.
7. Switch the adapter with a feature flag; retain the source snapshot until acceptance.

## Rollback

- Do not dual-write patient records initially.
- During cutover, keep SQLite/source read-only and preserve the migration manifest.
- Roll back application traffic to the previous adapter only before new production writes are accepted.
- After writes begin, restore PostgreSQL through its backup/PITR process rather than reverse-copying into SQLite.

## Production controls

- TLS-required connections, encrypted volumes, managed credentials, rotation, automated backups, point-in-time recovery, query logging with health-data redaction, pool limits, and restore drills.
- Consider PostgreSQL row-level security as defense-in-depth, while keeping authorization in the domain/API layer and testing both.
